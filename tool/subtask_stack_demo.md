# 子任务栈（Subtask Stack）可行性实测

> 2026-11-02 · 用真实 API 跑的小实验，**未改动任何产品代码**
> 脚本：`.test/demo_subtask_stack.py`（`.test/` 未入库，可按本文复现）

## 要验证什么

用户提出的机制：维护一个「进行中的子任务」栈，模型可以压栈/弹栈。

- **压栈**：保存当前上下文检查点，进入子任务（该子任务只看到自己的输入）
- **弹栈**：丢弃子任务上下文，回滚到检查点，并追加一段 `return`

猜想：这样能把「中间产物」挡在主上下文之外，从而省 token。

## 实验设计

**场景**：N 份运维日志（每份约 1.2KB），每份埋一个关键指标，最后要求汇总。

**A 平铺（现状）**：N 份日志依次堆进同一上下文，带着全部历史回答。

**B 子任务栈**：每份日志在独立上下文处理，只回传 ≤40 字要点；主上下文只有要点。

**度量**：读 API 返回的 `usage`（prompt / cached / completion），
按 `settings.json` 里 flash 的**峰时**单价折算（元/百万 token）。

## 结果

| 规模 | 策略 | prompt | cache 命中 | completion | 总 token | 费用 ¥ | 正确性 |
|---|---|---|---|---|---|---|---|
| **3 份** | A 平铺 | 9,934 | 8,704 | 3,329 | 13,263 | 0.0294 | 3/3 |
| | B 子任务栈 | 1,401 | 768 | 887 | 2,288 | 0.0084 | 3/3 |
| | **节省** | **-85.9%** | | | -82.7% | **-71.5%** | |
| **6 份** | A 平铺 | 31,407 | 28,544 | 6,349 | 37,756 | 0.0577 | 6/6 |
| | B 子任务栈 | 2,728 | 1,536 | 1,305 | 4,033 | 0.0129 | **5/6** |
| | **节省** | **-91.3%** | | | -89.3% | **-77.7%** | |

逐轮 prompt 的形状很说明问题：

```
A（线性膨胀）: 413 → 1530 → 2932 → 4340 → 5874 → 7510 → 8808
B（恒定）    : 419 →  417 →  418 →  420 →  418 →  418 →  218
```

## 三个结论

### 1. 节省是真的，且随深度放大

3 份省 71%，6 份省 78%（费用口径）。任务越长、中间产物越大，差距越大。

### 2. 缓存会吃掉一部分收益

A 的缓存命中率约 **91%**（前缀高度重复），所以「输入 token 省 91%」只兑现成
「费用省 78%」。**评估收益不能只看 token，要看费用。**

### 3. `return` 的保真度是命门

6 份时 **B 漏了一个指标**（`超时阈值 = 3.2s`）。原因正是 return 限 40 字，
子任务把那条压缩掉了。

> 省 78% 的钱，但答错 1/6 —— 这个交换不划算。所以机制必须配套约束。

## 若要产品化，建议

1. **`return` 用结构化字段**：`{结论, 证据, 键值对, 下一步}`，不要自由文本。
2. **主上下文维护键值台账**：弹栈时校验必填项（例如任务开始时声明的 key），
   缺了就让子任务重做/补交。
3. **深度上限 3**：更深容易丢上下文，收益也趋于饱和。
4. **`return` 必须追加在检查点之后**：这样主上下文前缀不变，最大化缓存命中。
5. **明确"回滚的是上下文，不是世界"**：子任务里改的文件、跑的进程不会撤销。
